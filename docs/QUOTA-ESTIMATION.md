# 额度预估口径：取舍与实测验证

用户问题：除了照搬 macOS 版的「支出 ÷ 点数增量 × 预算点」标定，有没有**更好的额度预估方式**？

结论先行：**在 Windows 上，最好的额度用量口径不是"预估"，而是直接用 `/v1/limits` 的
原始额度点 `used / budget`——它是上游权威值，零预估误差。** 本项目已把它作为主口径
（进度条、百分比、点数副行都用它）。美元只是它的一层换算，不引入额外误差；美元满额的
标定经实测与账本支出吻合到 1% 以内。下面是三种口径的实测对照与推导。

## 三种口径

| 口径 | 怎么来 | 误差来源 |
|---|---|---|
| **点数权威** | `/v1/limits` 的 `used / budget` | 无——上游直接给的绝对值 |
| **美元折算** | `满额USD × 点数百分比`（`scaledSpentUSD`） | 与点数权威同分母，恒等；不引入额外误差 |
| **账本实测** | 本机 transcript + 网关账本累加的等价美元（`spentUSD`） | 漏记子代理/标题生成等约 18%；scoped 窗口漏声明前支出 |

## 实测对照（本机，2026-08-27）

```
5h        点数权威 3.05% | 美元折算 3.05% | 账本实测 3.04%
7d        点数权威 0.88% | 美元折算 0.88% | 账本实测 0.88%
7d_fable  点数权威 0.80% | 美元折算 0.80% | 账本实测 0.53%
单价 0.00377 美元/额度点（账本支出 ÷ 已用点数反推，跨窗口自洽）
```

读出三件事：

1. **点数权威 = 美元折算**（5h 3.05=3.05，7d 0.88=0.88）。因为美元折算按
   `满额 × 点数百分比` 算，与点数权威同一个分母，数学上恒等——**换算成美元不会让用量
   口径变得更不准**。这否定了"美元口径会引入预估误差"的担心。

2. **点数权威 ≈ 账本实测**（5h 3.05 vs 3.04，7d 0.88 vs 0.88，差 <1%）。账本从
   token 独立累加出的支出，与上游点数高度一致——说明标定出的满额可信，两条独立数据源
   互为交叉验证。

3. **7d_fable 账本偏低**（0.80 vs 0.53）是**已知口径差**，非预估错误：modelScoped
   窗口的账本分桶只从"档位声明时刻"起累积（provider 首次见到该窗口才开始单独记账），
   声明前的支出无从追认。控件因此把账本值降为副行、点数权威作主行——正是为了让这类
   系统性偏差不污染主口径。

## 为什么 macOS 版要"预估"，而 Windows 版不必

macOS 版早期没有 `/v1/limits`，只能读 relay 帧的百分比（0.1% 分辨率），满额靠
「支出 ÷ 百分比增量 × 100」反推——那是被迫的预估。现在 `/v1/limits` 直接给原始点数，
用量口径不再需要任何反推。本项目保留标定，只为把**美元满额**这一层换算做出来
（点数是 Mirasim 内部单位，"1 点 = ? 美元"没有公开换算率，只能由账本反推）。

## 探索过的、更优单价来源

- **models.dev 的 token 单价**：已用于账本折算的分子（每次调用的美元 = token × 单价），
  这一层是权威的。但"额度点 → 美元"仍需一个换算率，models.dev 不提供。
- **多窗口交叉解单价**：5h 与 7d 反推的每点美元应同量级，本项目用它做**自洽核验**
  （离散超 4× 判账本与点数不自洽，停用兜底单价，见 `coherence.mjs`），而非取平均——
  取平均会把失真的一侧混进来。实测本机跨窗口 $0.00377 一致，核验通过。
- **打满外推（ETA）**：用近 1 小时点增速线性外推。对突发负载敏感，但"还剩多久打满"
  只需量级正确，线性足够；窗口重置后旧轨迹自然失配、从头积累。

## 一句话

有 `/v1/limits` 时，额度用量别预估——直接用点数。预估只留给"美元"这层换算，
且要有账本交叉验证与跨窗口自洽核验兜底，而不是单点信任一个反推值。

## 多机账本合并（v0.5）

点数是账号级、账本是本机级——账号在多台机器共用额度时，本页所有「账本$ ÷ 点数」
口径的分子都系统性偏低。v0.5 起可选启用多机账本同步：各机器把账本聚合态作为分片经
私有 Git 仓互读，标定/归因/强度的分子改用全机合计，标定观测另设「全覆盖」门。
原理、部署与故障表现见 [MULTI-MACHINE.md](MULTI-MACHINE.md)；未配置时行为与本页描述
完全一致。

## 档位倍率：网关按什么扣点（v0.9，2026-09-02 实测判定）

官方说明「fable 资源紧张，额度按 2 倍计量」。但"2 倍"相对什么？三种可能在数字上可分辨——
关键是 **Fable 5 官方价 $10/$50，正好是 Opus 5 的 $5/$25 的 2 倍**：

| 解释 | 预测「非 fable 每点美元 ÷ fable 每点美元」 |
|---|---|
| 点数按 **API 等价美元**计（与模型无关），fable 再额外 ×2 | 2.0 |
| 点数按 token 计，fable 与 opus 一视同仁 | 0.5（fable 每点买到的美元反而更多） |
| 点数按 token 计，fable 额外 ×2 | 1.0 |

本机实测（7d 窗，多机合并账本）：**2.009** → 第一种。
即同样 1 美元的 API 等价价值，走 fable 扣 2 份额度、走 opus/sonnet 扣 1 份。

独立佐证：5h 窗 fable 占支出 28.7%、7d 窗占 47.8%，模型构成差别很大，按 2× 折算后
基准单价分别落在 0.010000 与 0.009968 $/点；官方 max 40x 宣称的 5600 ÷ 560000 = **0.010000**。
若点数按 token 计，两个构成不同的窗口不可能同时命中同一个值。

因此：**满额口径 = 折算后的基准单价 × 预算点**，与官方「不用 fable 时一周 5600 刀」同口径
（本机算得 $5582，差 0.3%）。倍率在应用「口径」页可改，默认 2，存 `~/.miraquota/settings.json`；
官方日后调整比例，改这里即可，不必改代码。实现见 `provider/lib/settings.mjs`、`coherence.mjs`。
