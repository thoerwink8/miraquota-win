# 额度预估口径：取舍与实测验证

用户问题：除了照搬 macOS 版的「支出 ÷ 点数增量 × 预算点」标定，有没有**更好的额度预估方式**？

结论先行：**在 Windows 上，最好的额度用量口径不是"预估"，而是直接用 `/v1/limits` 的
原始额度点 `used / budget`——它是上游权威值，零预估误差。** 本项目已把它作为主口径
（进度条、百分比、点数副行都用它）。美元只是它的一层换算，不引入额外误差；美元满额的
标定经实测与账本支出吻合到 1% 以内。下面是三种口径的实测对照与推导。

## 三种口径

| 口径 | 怎么来 | 误差来源 |
|---|---|---|
| **点数权威** | `/v1/limits` 的 `used / budget` | 无——上游直接给的绝对值 |
| **美元折算** | `满额USD × 点数百分比`（`scaledSpentUSD`） | 与点数权威同分母，恒等；不引入额外误差 |
| **账本实测** | 本机 transcript + 网关账本累加的等价美元（`spentUSD`） | 漏记子代理/标题生成等约 18%；scoped 窗口漏声明前支出 |

## 实测对照（本机，2026-08-27）

```
5h        点数权威 3.05% | 美元折算 3.05% | 账本实测 3.04%
7d        点数权威 0.88% | 美元折算 0.88% | 账本实测 0.88%
7d_fable  点数权威 0.80% | 美元折算 0.80% | 账本实测 0.53%
单价 0.00377 美元/额度点（账本支出 ÷ 已用点数反推，跨窗口自洽）
```

读出三件事：

1. **点数权威 = 美元折算**（5h 3.05=3.05，7d 0.88=0.88）。因为美元折算按
   `满额 × 点数百分比` 算，与点数权威同一个分母，数学上恒等——**换算成美元不会让用量
   口径变得更不准**。这否定了"美元口径会引入预估误差"的担心。

2. **点数权威 ≈ 账本实测**（5h 3.05 vs 3.04，7d 0.88 vs 0.88，差 <1%）。账本从
   token 独立累加出的支出，与上游点数高度一致——说明标定出的满额可信，两条独立数据源
   互为交叉验证。

3. **7d_fable 账本偏低**（0.80 vs 0.53）是**已知口径差**，非预估错误：modelScoped
   窗口的账本分桶只从"档位声明时刻"起累积（provider 首次见到该窗口才开始单独记账），
   声明前的支出无从追认。控件因此把账本值降为副行、点数权威作主行——正是为了让这类
   系统性偏差不污染主口径。

## 为什么 macOS 版要"预估"，而 Windows 版不必

macOS 版早期没有 `/v1/limits`，只能读 relay 帧的百分比（0.1% 分辨率），满额靠
「支出 ÷ 百分比增量 × 100」反推——那是被迫的预估。现在 `/v1/limits` 直接给原始点数，
用量口径不再需要任何反推。本项目保留标定，只为把**美元满额**这一层换算做出来
（点数是 Mirasim 内部单位，"1 点 = ? 美元"没有公开换算率，只能由账本反推）。

## 探索过的、更优单价来源

- **models.dev 的 token 单价**：已用于账本折算的分子（每次调用的美元 = token × 单价），
  这一层是权威的。但"额度点 → 美元"仍需一个换算率，models.dev 不提供。
- **多窗口交叉解单价**：5h 与 7d 反推的每点美元应同量级，本项目用它做**自洽核验**
  （离散超 4× 判账本与点数不自洽，停用兜底单价，见 `coherence.mjs`），而非取平均——
  取平均会把失真的一侧混进来。实测本机跨窗口 $0.00377 一致，核验通过。
- **打满外推（ETA）**：用近 1 小时点增速线性外推。对突发负载敏感，但"还剩多久打满"
  只需量级正确，线性足够；窗口重置后旧轨迹自然失配、从头积累。

## 一句话

有 `/v1/limits` 时，额度用量别预估——直接用点数。预估只留给"美元"这层换算，
且要有账本交叉验证与跨窗口自洽核验兜底，而不是单点信任一个反推值。

## 多机账本合并（v0.5）

点数是账号级、账本是本机级——账号在多台机器共用额度时，本页所有「账本$ ÷ 点数」
口径的分子都系统性偏低。v0.5 起可选启用多机账本同步：各机器把账本聚合态作为分片经
私有 Git 仓互读，标定/归因/强度的分子改用全机合计，标定观测另设「全覆盖」门。
原理、部署与故障表现见 [MULTI-MACHINE.md](MULTI-MACHINE.md)；未配置时行为与本页描述
完全一致。

## 档位倍率：网关按什么扣点（v0.9，2026-09-02 实测判定）

官方说明「fable 资源紧张，额度按 2 倍计量」。但"2 倍"相对什么？三种可能在数字上可分辨——
关键是 **Fable 5 官方价 $10/$50，正好是 Opus 5 的 $5/$25 的 2 倍**：

| 解释 | 预测「非 fable 每点美元 ÷ fable 每点美元」 |
|---|---|
| 点数按 **API 等价美元**计（与模型无关），fable 再额外 ×2 | 2.0 |
| 点数按 token 计，fable 与 opus 一视同仁 | 0.5（fable 每点买到的美元反而更多） |
| 点数按 token 计，fable 额外 ×2 | 1.0 |

本机实测（7d 窗，多机合并账本）：**2.009** → 第一种。
即同样 1 美元的 API 等价价值，走 fable 扣 2 份额度、走 opus/sonnet 扣 1 份。

独立佐证：5h 窗 fable 占支出 28.7%、7d 窗占 47.8%，模型构成差别很大，按 2× 折算后
基准单价分别落在 0.010000 与 0.009968 $/点；官方 max 40x 宣称的 5600 ÷ 560000 = **0.010000**。
若点数按 token 计，两个构成不同的窗口不可能同时命中同一个值。

因此倍率成立。倍率在应用「口径」页可改，默认 2，存 `~/.miraquota/settings.json`；
官方日后调整比例，改这里即可，不必改代码。实现见 `provider/lib/settings.mjs`。

### 倍率怎么量才准（2026-09-22 改，起因：「fable5.1 和 fable5 的倍率一直算不准」）

上面那个 2.009 是**整窗总量相除**（非该组单价 ÷ 该组单价）算出来的。它长期在 1.8–2.4
之间晃，因为两个比值各自都带着他机用量、账本与官方计数器的时间错位，相除把误差乘了起来；
更早还叠着一层跨源双计（见下一节）。粒度也只到「fable 这个词」，`claude-fable-5` 与
`claude-fable-5-1` 并在一个桶里，结构上问不出两者各自的倍率。

现在的量法（`provider/lib/rate-measure.mjs`）：

1. 读 `/v1/limits` 的同一个 tick 上，把**各模型累计美元**一起记下（`Calibrator.marks`）；
2. 只取「这一段只有一个模型在花钱」的采样段，逐段算 `Δ点数 ÷ Δ美元 ÷ 100`；
3. 按美元加权取**中位数**——错位段（实测里会出现 40 点/$ 或 443 点/$）被中位数整掉；
4. 每个模型一行给出，档位组值是组内各模型的加权中位；两款量得不一致时界面明说。

本机实测（回放 63 段、$74；那一次配的还是「收尾那条 mark」，见下）：`claude-fable-5-1` =
**×2.000 整**（p75 也是 2.00）。`claude-fable-5` 这个窗口里没跑，如实显示样本不足，
不再拿 5.1 的数冒充它。段内求和那版改完后**段数会变**（每段要求两端都踩在 mark 上，凑不齐
的丢掉），界面按实采的 mark 给数。

另有一条**可复现**的量法落在仓里：`node scripts/verify-rate.mjs`（只读原始记录，状态写临时
目录，不碰 ~/.miraquota，随时可跑）。它拿真实 transcript + 真 `/v1/limits` 采样按「整条链
望远镜相消」算，并把旧的「两源并集」口径并排给出——2026-09-23 实跑：

| 窗口 | 模型 | 新口径（transcript） | 旧口径（两源并集） |
|---|---|---|---|
| 7d | claude-fable-5-1 | 74 段 $72.18 → **×1.923** | $128.02 → ×1.084 |
| 7d_fable | claude-fable-5-1 | 73 段 $71.92 → **×1.843** | $127.64 → ×1.038 |
| 5h | claude-fable-5-1 | 29 段 $21.63 → **×1.998** | $42.86 → ×1.008 |
| 7d | claude-opus-5 | 61 段 $57.46 → **×1.001** | $91.77 → ×0.627 |
| 5h | claude-opus-5 | 57 段 $53.68 → **×0.991** | $87.23 → ×0.610 |

这张表就是这次改动的全部证据：**fable 与 opus 同时回到各自的真值**（2 与 1）——说明偏差
出在美元口径上，不是某个模型的价目填错。旧口径的美元虚高 1.77×（fable）/ 1.60×（opus），
于是 fable 量成 1.0 上下、opus 量成 0.6，而「组内 ÷ 组外」那版把这个比例搅成一个天天漂的
2.39。fable 那几个值散在 1.84–2.26 是**他机污染**（点数是账号级、账本是本机级），所以看
一批窗口的中心值，不看单个数。

**为什么分子分母必须同一瞬**：账本按分钟聚合，官方 `used` 每 30 秒采一次；用分钟桶配
采样区间，边界最多差 60 秒，而一段常常只有两三分钟——同一批数据这么算出来 p25/p75 散到
0.97/3.27。改成 tick 上取累计值相减后，段内的分子分母是同一个时间窗，才有 2.000 这种数。

**一段的美元是段内所有 mark 之和，不是收尾那一条。** mark 记的是**增量**（相对上一条
mark），而点数样本的间隔门与 mark 的间隔门原先各自独立：某款模型这一轮值没变，就只记
mark 不记点数。于是 `(a, b]` 里能有好几条 mark，只取 `b` 那一条会把这一段算成 5×（漏掉的
增量让分母变小）。两处一起改才对得上：

- `Calibrator.record` 让 **mark 当节拍器**——没落 mark 的那一轮，点数样本也不记，于是每个
  样本都踩在 mark 上，段内把 mark 增量累加即恰好等于 `(a.at, b.at]` 的花费（望远镜求和）；
- 估算器要求**两端都踩在 mark 上**，段内有任何一条 `gap`（重启、桶被修剪，累计基准断了）
  就整段丢弃。改这版之前存下的点数样本端点在节拍之外，会被丢掉而不是算错——宁可样本少。

这两条各自都有契约测试（`test/point-cost.test.mjs`：段内求和、点数只落 mark 节拍）。

## 美元只认一个来源（2026-09-22）

原先 transcript 与 Mirasim 网关账本取并集，靠「transcript 的 `requestId` == 网关的
`providerCallId`」跨源去重。这个等式已经不成立：网关现在把 `providerCallId` 写成 relay
自己的调用 id（与同行 `relayCallId` 同值），而 transcript 有三分之一的行没有 `requestId`、
只能退回 `message.id`——**两侧 id 交集为 0**，于是同一次调用两边各记一次。

实测（2026-09-21 13:13 起）：

| 模型 | 直扫 transcript | 当时的账本 | 虚高 |
|---|---|---|---|
| claude-fable-5-1 | $395.24 | $630.21 | 1.59× |
| claude-sonnet-5 | $67.68 | $99.24 | 1.47× |
| claude-opus-5 | $74.15 | $88.20 | 1.19× |

虚高倍数随两个来源各自的覆盖比例天天漂，所有按美元算的量跟着漂。现在的规矩：

- **Claude Code 的调用只认 transcript**（token 完整、可回溯全部历史）；
- 网关那份进影子账，只回答「网关看到的比 transcript 多吗」——多了就是 transcript 漏了
  （换过 HOME、SDK 起的会话不写会话文件），在「口径」页点名；
- **dispatch 例外**：Mirasim 自己发的中继调用不写任何会话文件，只有网关有，照旧从网关入账；
- codex 等没有 transcript 覆盖的 agent 也照旧从网关入账。

判据是可验的：只用 transcript 的美元，官方点数增量 ÷ 美元正好落在 200.0 点/$（fable 的
2 倍计量），说明 transcript 一侧就是全额。**复现：`node scripts/verify-rate.mjs`**——它把
新旧两个口径并排算出来（见上一节那张表：fable 1.92 vs 1.08、opus 1.00 vs 0.63）。
账本状态因此升到 schema 3——旧聚合里每笔 Claude 调用都记了两次，拆不开，只能清空重扫
（加载时自动清空并重扫，有契约测试盯着）。**服务器那台也要升到这版并重建**，否则它推上来
的分片还带着旧的虚高；外机分片还是旧口径时，界面在「口径」页点名（`staleForeignShards`）——
合并口径会把那份虚高算进账号合计，本机修好了也白修。

## 价目表：缓存读不能按 10% 推（2026-09-22）

`claude-fable-5-1` 与 `claude-fable-5` 输入输出同价（$10/$50），但**缓存读差 4 倍**
（$0.25 vs $1.00）；`claude-opus-5-5` 是 $4/$20、缓存读 $0.20（不是 $4 的 10%）。
本机实测缓存读占 fable 花费的 56%，这一列填错，账本和倍率一起废。

两条闸：内置表逐项照官方价目填（`provider/lib/pricing.mjs` 的 `BUILTIN`）；没收录的模型
走前缀/系列兜底时**记下来并在界面点名**（`guessedModels()`）——兜底是静默成功的，
它返回一个看着合理的价，以前没有任何落点。`claude-opus-5-5` 就是这么按 Opus 5 记了一阵。

## 满额口径：官方除法（v0.9.19，2026-09-02 用户向官方求证后改）

官方确认：**额度点 ÷ 100 = 该点数对应的美元额度**。所以

    满额 = 预算点 ÷ 100 ÷ 档位倍率        （总窗倍率为 1）

    7d       560,000 ÷ 100        = $5,600
    5h       156,800 ÷ 100        = $1,568
    7d_fable 296,800 ÷ 100 ÷ 2    = $1,484

**那三个预算点是 2026-09-02 的快照，不是常量。** 2026-09-23 实测 `/v1/limits`：三个窗
同时缩到 ×0.9154——7d 512,600、5h 143,528、7d_fable 271,678（512600/560000 =
143528/156800 = 271678/296800，误差 0，是按同一个系数整体缩的，不是结构调整），一周从
$5,600 变 **$5,126**。同一天还多出一个 `7d_claude` 窗，满额与 7d 池相同（512,600）——
满额相同说明它不构成新的约束，只是「Claude 家族花了多少」的分档读数；`7d_fable` 仍是
唯一有独立上限的子池。代码从来不把这几个数当常量：满额算的是 `budget × 0.01 ÷ 倍率`，
`budget` 每帧从 `/v1/limits` 读，官方缩放它、界面跟着动。本页与 `engine.mjs` 注释里的
算例沿用 2026-09-02 那组数，只用来讲清口径；**「÷100 三窗都整除」在新值上不再成立**
（143528 ÷ 100 = 1435.28），整除只是那组快照的巧合。

档位窗为什么再除倍率：那 296,800 点的子上限**按额度价值**是 $2,968，但 fable 每花 1 美元
扣 2 点，真拿 fable 去花只花得掉 $1,484。用户 2026-09-02 在两个口径里选了后者——这样
fable 那张卡整块活在「真实 fable 美元」这把尺上，能直接和主行的账本花费比。代价是它与
总窗的 $5,600（"完全不碰 fable"口径）不是一把尺，卡上要说清。

**为什么废掉此前的账本反推**（满额 = 账本支出 ÷ 已用点 × 预算点）：

1. 账本只要漏记一点，满额就同倍缩水。实测反推 0.009645，满额算出 $5,401，偏官方 -3.5%
   （漏的是未归因点数、relay 尚未回填的 token、他机分片延迟）。
2. Mirasim 一停，推算路径退回另一套「分段单价中位数」算法，与实测路径两套数。用户
   2026-09-02 截图里 7d 报 $2,837 而非 $5,600 就是这条路径。官方除法只依赖预算点，
   锚点里就带着，三条 payload 路径同一个数。

反推**不删**，降级为对账检查：它与 0.01 的偏离就是「本机账本漏了多少」的读数，界面在
「口径 → 单价 → 账本对表」给出，偏低超过 2% 会直说主行的花费数字该往上看。

#### 实测一次逐点对上（2026-09-08，fable）

服务器那台（vmi3551059）在 7d_fable 里是唯一花钱的机器，拿它自己的账本与官方对表：

| | 值 |
|---|---|
| 官方 `7d_fable.used` | 5166.9534 点 |
| 本机账本 fable 支出 × 2 × 100 | 5167 点 |
| 偏差 | 0.05 点（0.001%） |

结论：**账本口径本身是准的**，前面说的「实测偏低约 3%」是漏记（未归因点数、relay 尚未
回填的 token、分片延迟）而不是折算错。复现：`node scripts/probe-fable.mjs --from <窗口起点>`
（干净状态文件全量重扫，先开 fable 档位组再 refresh）。

**对表前先确认窗口起点。** 官方三个窗口都是定长定点的，起点 = `reset_at − 时长`。账号
周期一重置，`7d` 的起点会和 `5h` 一样是刚刚——那天三个窗口的 `reset_at` 全指向
03:28:54Z，`7d` 里只装着 1.1 小时的量。拿日历「最近 7 天」去比，分子大出一个数量级
（$1050 对 $26），看着像账本坏了。


### 「2 倍」还是「4 倍」——同一件事的两种口径

群里流传过「opus 2 倍、fable 4 倍」的说法。它与上面的判定**不矛盾**，差别只在计量单位：

| 模型 | 官方 API 输出价 /M | 额外倍率 | 每 M 输出扣点 | 相对 Opus |
|---|---|---|---|---|
| Haiku 4.5 | $5 | 1× | 500 | 0.2× |
| Sonnet 5 | $10 | 1× | 1,000 | 0.4× |
| Opus 5 | $25 | 1× | 2,500 | 1× |
| Fable 5.1 | $50 | **2×** | 10,000 | **4×** |

- **每美元**口径：fable = 2× opus。这是官方的说法，也是设置里那个倍率的口径，**填 2**。
- **每 token** 口径：fable = 4× opus。因为 fable 标价本身就是 opus 的两倍，之上再罚两倍。

把 4 填进设置会让所有美元数一起翻倍，所以「口径」页那行说明必须留着（有契约测试盯）。

「opus 也是 2 倍」这半句需要一个 1× 基准，而按官方标价没有哪个模型能让 opus=2 且
fable=4 同时成立（以 Sonnet 5 为 1× 时是 2.5 与 10）。若真存在一个「1× 档 = $0.02/点」，
sonnet/haiku 一周就能兑 $11,200，官方那句 5600 就得是 opus 专属数字，与官方自己的 4116
算例（47%×5600 + 53%×5600÷2）对不上。本机数据无法直接证伪——点数归因只到
claude/gpt 家族，分不出 opus 与 haiku——但两条旁证都不支持它。
