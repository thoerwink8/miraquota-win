## 提示词正文

你现在的任务**不是写代码**，是**审计**：把这个项目自己"写下去的东西"盘一遍，判断哪些值得改成
SQLite，哪些不该动，然后给我一份带数字的结论。除非我说"开始改"，否则不要动实现。

### 一、背景：参考实现在哪、它解决了什么

另一个项目（miraquota-win）刚把它的账单类持久化从「JSON 聚合态」改成「SQLite 逐笔流水账」。
它的代码与约定可以读，路径在 `D:\frank\miraquota-win`：

| 读什么 | 为什么读 |
|---|---|
| `docs/STORE.md` | 机制约定：8 条契约、审计结论、磁盘实测表、迁机器三步 |
| `provider/lib/store.mjs` | schema、去重、口径视图、保留、打包。**注释里记着踩过的坑** |
| `provider/lib/sources.mjs` | 原始记录 → 流水行；游标只影响性能不影响正确性 |
| `provider/lib/journal-ledger.mjs` | 怎么让新存储套上旧接口（换实现不换业务） |
| `scripts/store-migrate.mjs` | 迁移/对账/任务报表/打包校验，一条路服务三件事 |
| `test/store.test.mjs`、`test/store-cli.test.mjs` | 13 条契约，看"什么必须为真" |

它换存储的**理由**（不是"SQLite 更时髦"）：① 聚合态被当成账本存，于是换一次口径就要清空重建
8 天；② 去重键占掉状态文件 75–85% 的体积；③ 没有会话/任务维度，所以"每个任务花了多少"结构上
问不出来。三条都是**具体事故**逼出来的，不是设计洁癖。

### 二、先审计：这个项目到底写了哪些东西

用命令查，不要凭印象。至少覆盖：源码里所有 `writeFileSync`/`appendFileSync`/`createWriteStream`、
所有 `*.json`/`*.jsonl`/`*.log`/`*.db` 落点、`~` 下的状态目录、以及构建产物。

对每一个落点给出：

| 字段 | 说明 |
|---|---|
| 路径 | 实际路径（含 `~` 展开） |
| 是什么 | 一句话 |
| 格式 | JSON / JSONL / 多小文件 / SQLite / 日志 |
| 体积 | 现在多大；**增长率**（每条/每天多少字节，按最近数据估） |
| 谁写 | 几个写入者（多进程写同一个文件是重点，容易静默丢数据） |
| 谁读 | 哪些模块读；读的形状（全量读？按时间范围？按维度聚合？） |
| 保留 | 现在留多久、有没有清理、清理靠谁 |
| 可重建 | 删掉之后能不能从别的原始记录重算出来（**这条决定迁移能不能破坏性做**） |

然后把它归到四类里的一类：

1. **流水/事实**：一次操作一行，是唯一真相，删了就没了；
2. **聚合/视图**：能从①算出来；
3. **配置/密钥**：人要能手改、或者不该进库；
4. **一次性草稿**：临时产物、日志、调试转储。

### 三、判断标准（什么时候该进 SQLite，什么时候不该）

**值得进库**（满足两条以上）：

- 体积随行数线性增长，而且**要按维度查**（按时间/按任务/按模型/按机器拆）；
- 需要去重（同一条记录会被重复读进来）；
- 需要保留期管理（老的降精度、更老的删掉）；
- 多写入者写同一个文件（现在靠"读-改-写整个 JSON"，迟早互相覆盖）；
- 现在为了查询而全量加载进内存。

**不该进库**：

- 单文件几十行、人还要手改的配置（`settings.json` 这种）——留 JSON 更省事；
- 密钥、令牌、口令——**不要进库**（备份/同步会把它们带出去）；
- 纯缓存，删了能重算——考虑直接删掉，而不是换个格式存；
- 一次性草稿/日志——该做的是清理，不是建表。

**判断"要不要改"的时候，先回答这个问题**：现在的形状有没有**已经发生过**的具体损失
（丢数据、算错数、慢到不能用、磁盘失控）？如果答不上来，结论就写"不改"，并说明理由。
不要为了统一而统一。

### 四、如果结论是"改"：方案要写清这五件事

1. **schema 草案**：表、主键、索引、以及"口径"放在哪（聚合是视图还是表）；
2. **迁移路径**：从原始记录重扫，还是就地迁移？如果原始记录可能已经被清理，
   就必须先做就地迁移（并且要有回滚）；
3. **验证方式**：迁移前后**总额守恒**（分文不差）、磁盘前后对比、以及一条端到端测试；
4. **保留策略**：明细留多久、汇总留多久、各自的磁盘代价（按实测的字节/行算，不要拍）；
5. **风险与回滚**：谁在读、改的时候会不会读到半成品、怎么退回去。

### 五、必须避开的坑（都在参考实现里踩过，注释里写了）

1. **`db.exec()` 不绑定参数**：SQL 里的 `?` 会当 NULL，`WHERE day < ?` 恒为假——
   汇总静默插 0 行，紧接着把明细删了，数据永久丢失。要用 `prepare().run(...)`。
2. **`WITHOUT ROWID` 表的主键列隐含 NOT NULL**：含 NULL 的行整条插不进去；
   而且主键必须覆盖**汇总的每一个分组列**，少一列就是"后者覆盖前者"的静默丢数。
3. **长字符串做主键会放大整个库**：WITHOUT ROWID 表的每个二级索引项里都嵌着主键原文。
   把重复出现的字符串（会话 uuid、路径、模型名）拆进维度表、用整数 id 引用，
   实测从 945 字节/行降到 155。
4. **汇总粒度必须与口径粒度一致**：按天汇总 + 逐小时取大，会让历史区间**恒偏低**
   （实测 0.15%）。对账工具不允许有方向性的偏差。
5. **别把"能重建的聚合"当账本存**：一旦口径被烧进数据里，改口径就得清空重建。

### 六、这个项目的具体线索（我只做了粗看，你要自己确认）

- **windsurf-dao**：`ledger/` 下有几百个 `*-backfill.json`（每个 0.4–0.7 KB，看起来是一次运行一个
  文件）；`_flow/` 3.9 MB 的临时 JSON 与日志（`wl.json` 650 KB、`inbox.log` 1.8 MB、
  `cmd-escape.jsonl` 140 KB）；还有 `schemas/`、`policy/`、`host/`、`packages/`。
  重点判断：**那个 `ledger/` 是不是"流水"**（如果是，几百个小文件的形状本身就值得改），
  以及 `_flow/` 里哪些是草稿、哪些其实是事实。
- **ai-gateway-stack**：`deploy/`、`services/`、`scripts/`、`secrets/`，以及 `_tem/`。
  注意 `_tem/new-api-src` 是 1.1 GB 的 **vendored 源码**，不是状态，别碰。
  这个项目更像部署栈：它的"状态"可能主要在远端机器上——**先确认状态在哪台机器上**，
  再谈要不要改。

### 七、交付物

一份**审计表**（上面第二节那张，逐行填）+ 每个落点一句结论（改 / 不改 / 删，附理由）+
对"要改"的那些给第四节的五项方案。最后用一段话回答：**这个项目现在的持久化形状，
有没有已经造成过实际损失？** 有就举出来（哪个文件、什么现象、什么时候），没有就直说没有。

先给结论和方案，别动代码。
